keykaren: The task focuses on lightweight collaboration features including conflict visualization, version history, persistent edit logging, and presence awareness — without requiring user authentication. Each participant is assigned a temporary session identity to display online editors.

Functional Requirements

1. Real-time Collaboration

Multiple users can collaboratively edit the same document concurrently.
New documents can be created, each representing an independent shared editing session.
Changes propagate to all connected clients in real time through WebSockets (Flask-SocketIO).
Document content updates instantly across all active clients.

2. Concurrency Handling

Use a simplified Last-Write-Wins (LWW) strategy.
The server accepts the most recently received update as authoritative.
All clients are updated with the resulting document state.

3. User Presence Awareness

No login required — each visitor automatically receives a temporary anonymous user ID.
Display how many users are currently editing a given document.
Presence counts update dynamically when users join/leave.

4. Edit Debouncing (Client-Side Optimization)

A 400 ms debounce is applied before sending updates to the server to prevent excessive events.
Continuous typing resets the timer and batches changes efficiently.

5. Persistence & Edit Logging

The current state of each document is stored persistently on disk.
Every edit is written as an append-only record in:
On server startup, the application rebuilds document content and version information by replaying JSONL logs.

6. Conflict Visualization

A conflict occurs when multiple users edit the same or adjacent lines within a short time window.
Server behavior:

Detect conflicts via timestamp + affected line indices.
Broadcast a conflict event to all connected users.
Client behavior:

Highlight conflicting text sections (e.g., red or yellow background).
Display console warnings for debugging.
Visualization is simulation-based, not a merge operation.

7. Anonymous User Identification

No authentication system is required.
Each connected session receives a short randomly-generated identity (e.g., user-1).
All edits and history records store this ID.

8. Other Requirements
Ability to generate reproducible test environments, e.g., requirements.txt, Dockerfile, setup.sh.
Ability to design automated test code to verify real-time collaboration, persistence, conflict handling, and multi-document behavior.
Automatic generation of runtime scripts (e.g., run_test.sh) for one-click testing.
Ability to output detailed test report templates for easy result analysis.
